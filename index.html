a kerberos failure, explained by breaking it

Kerberos has a five-minute wall

Make two machines disagree about the time by more than five minutes and Kerberos refuses to talk to you: right password, valid ticket, correct service name, denied anyway.

No complaint about passwords. Just: Clock skew too great.

01 · break the clocks

whose clock is wrong?

A Kerberos login is really two checks. First your client gets tickets from the KDC (kinit). Then it shows a ticket to the service. Each check compares your client's timestamp with that machine's clock. The KDC's clock is the reference; drag the other two and watch which stage fails.

Positive means that clock is ahead. The skew check is "more than the allowed amount", so a difference of exactly 5:00 still passes. Real clocks drift continuously; here you're freezing one moment. Error 37 is KRB_AP_ERR_SKEW; "typical message" lines are what MIT kinit and Java's GSS-API print.

02 · why five minutes

the wall is a memory limit

Every request carries an authenticator: a timestamp encrypted with the session key. If an attacker captured one, they could send it again. So services do two things: reject timestamps outside the window, and remember the authenticators they've already seen inside it. The window is how long they have to remember.

service replay cache

The trade: a wider window means services remember more for longer, and a replay has more time to work if that memory is missing. That's why the fix for a clock problem is never "raise the skew". Replay also needs an attacker who captured the request in the first place, so treat this as defense in depth rather than a headline attack.

03 · tickets have clocks too

a slow clock sees the future

Tickets carry their own start and end times, stamped by the KDC. The service compares them with its own clock, with the same allowance. A service whose clock is slow sees a fresh ticket as not valid yet. One whose clock is fast sees an almost-expired ticket as already dead.

scenario

Scenario times: the fresh ticket is 30 seconds old and the expiring one has 2 minutes left, each measured on the true clock. Allowed skew is 5:00 here.

04 · the usual suspects

how clocks go wrong

  • VM restored or resumedSnapshots, live migration and suspend/resume can leave a guest minutes (or hours) behind until something steps its clock.
  • Laptop sleptClients that sleep and wake on flaky networks can run on a stale clock until time sync catches up.
  • Time sync blocked or brokenA firewall rule, a dead NTP source or a stopped service leaves a host to drift on its own.
  • Containers inherit the hostA container has no clock of its own. If the host (or the VM under Docker Desktop) is off, so is everything inside.
  • "Fixing" the time zone by handKerberos timestamps are UTC, so a different zone is harmless. Setting the local time wrong to match a zone is not.
  • Different time sourcesTwo hosts both "synced", but to different sources that disagree with each other and with the KDC.

05 · find it, fix it

read the failure, then the clocks

  • Fails at kinit?The client and the KDC disagree. Fix the client (or the KDC). The service isn't involved yet.
  • kinit works but the connection fails?The client and KDC agree, so look at the service host's clock, then ticket start and end times (chapter 03).
  • Tempted to raise clockskew?Don't, except in a throwaway test config. It hides the problem and widens the replay window (chapter 02).

compare the clocks

# Linux — run on the client, the KDC and the service host, then compare
date -u                      # UTC time right now
timedatectl status           # is the system clock synchronized?
chronyc tracking             # how far off is it from its time source?

# Windows
w32tm /query /status
w32tm /stripchart /computer:dc.example.com /samples:5 /dataonly
w32tm /resync                # after fixing the time source

Prefer fixing the time source so every host follows the same one. Stepping a clock by hand (for example chronyc makestep) is fine as a one-off, but let time sync keep it right afterwards. Hostnames above are placeholders.
